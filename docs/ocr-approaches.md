# OCR approaches considered

Reviewed October 29, 2026. No representative user documents were provided, so no claim of production Khmer accuracy is made. The sample is useful for checking the pipeline, not measuring general accuracy.

| Approach | Strength | Limitation | Decision |
| --- | --- | --- | --- |
| Extract embedded PDF text / parse document XML | Quick; no OCR errors when Unicode mappings are correct | Broken PDF character maps, legacy Khmer encodings, and scanned pages can produce unusable text | Do not use as the default |
| Render pages + browser Tesseract LSTM | Works from visible glyphs; no API key; files can remain local; explicit Khmer model | CPU intensive; printed fonts and scan quality affect accuracy; complex layouts and handwriting need review | Implemented, using accurate/fast official models |
| LibreOffice + raster OCR | Preserves rendered Office layout before recognition, including document images | Needs a Node server and installed fonts; cannot recover glyphs that LibreOffice itself renders incorrectly | Implemented for DOC/DOCX/ODT/RTF |
| Google Cloud Vision `DOCUMENT_TEXT_DETECTION` | Official Khmer (`km`) support; worth comparing on difficult scans and layouts | Paid external service, credentials, document upload, service dependency; accuracy must be measured | Documented alternative; no hidden cloud fallback |
| Khmer-specific neural recognizer such as Netra-OCR | Model authors report promising Khmer line-recognition results | A separate inference runtime and full-page detection/layout pipeline; author benchmarks are not independent validation; training-data terms need review | Candidate for a later local inference service |
| General vision language model | Can interpret layouts and mixed visual material | May invent or normalize text; Khmer support and transcription accuracy vary; compute/API costs | Not the default for faithful transcription |

## Implemented pipeline

1. Validate the file type, size, and queue limits.
2. For Office files, render to PDF in LibreOffice. Return that PDF to the browser and remove temporary server data.
3. Render each PDF page with PDF.js at 300 DPI, or decode an uploaded image. Cap individual canvases to avoid excessive browser memory.
4. Optionally apply gentle grayscale/contrast adjustment. This is off by default because aggressive thresholding can erase fine Khmer marks.
5. Recognize with Khmer + English `tessdata_best` using the LSTM engine. Reuse the worker across a batch. Fast mode uses `tessdata_fast`, with a separate browser cache.
6. In Accurate mode, find text rows in the pixels and read each row on its own; this row reading is the primary result. Tesseract's whole-page segmentation can shred a clean Khmer line into one-to-three character fragments with high confidence, so the page reading supplies block/column order and is only kept when the rows visibly lost text, confidently read numbers or English words. Khmer rows are also read with the `script/Khmer` model, which is preferred unless it lost text. Confidence scores do not decide between the two models: on synthetic pages they ranked readings worse than always choosing the script model. Each single-line Khmer row is then read three more times (script model enlarged with lighter strokes, language model reduced with darker strokes, script model reduced) and the five readings are combined by a character-level plurality vote, ties going to the script model. Every voted character comes from a reading of the pixels. The vote may drop noise such as ruled lines read as letters, but it is rejected if it loses a confidently read number or English word. On the `test-files/` benchmark (`npm run benchmark:files`) this reduced character errors on three phone-scanned pages from 7.0% to 4.3%, and on a typed page from 0.41% to 0.27%. The variants were chosen on those same pages, so expect a smaller gain on other documents. Where at least two readings saw a different letter from the plurality, the Khmer word list from tessdata_best `khm.traineddata` (`static/ocr/khm-words.txt`, extracted with `combine_tessdata` and `dawg2wordlist`, about 150 KB compressed) picks the option that puts more of the line into known words. It only swaps one letter for another: letting it add or drop letters made it delete unknown letters and complete words that were not there. On the same benchmark this reduced errors on the scanned pages from 4.33% to 4.09% and on the typed page from 0.27% to 0.18%; with ten readings per line a simulation on saved readings gave 3.74% to 3.14%. Before rows are found, long thin ruled lines are erased from the page: the rule under a running header, underlines and boxes around headings (`src/lib/ocr-cleanup.ts`). Each was being read as `_`, `[` or `~~`, or joined to the text row beside it. A pixel is kept where a letter stroke crosses the line, and only the line's own rows are cleared where a letter rests on it. Lines in a grid remain the job of the table-ruling step. A row taller than usual is read as a block only when it holds more than one text line; a single large heading is read as a line and joins the vote. Together with lighter strokes in the enlarged script reading, which was chosen by scoring 21 reading variants on saved readings of the scanned pages, this reduced character errors on the three scanned pages from 4.09% to 3.50%, with the typed page unchanged at 0.18% and no extra time. Removing isolated specks, black-and-white conversion and sharpening were also measured; each made results worse and none is used. The decorative heading font on the scanned pages (for example ភ read as ទ in "ភពផែនដី") is misread by every model and variant, so it needs a model trained on that font rather than image preparation.
7. In Khmer modes, request word boxes and confidences. For Khmer lines with at most two Latin tokens, re-read uncertain Latin words (confidence below 80) from enlarged source-image crops, retaining the selected language model. Check at most 12 words per page. Accept a Khmer alternative only at confidence 85 or greater and an improvement of at least 20 points; retain and flag unresolved candidates. These thresholds are conservative heuristics, not calibrated probabilities. English phrases, confident English, and short uppercase acronyms are preserved. Per-crop segmentation settings are restored before the next page.
8. Normalize output to NFC and put Khmer marks in one standard order (`src/lib/khmer-normalize.ts`: subscripts before vowels, coeng-ro after other subscripts, register shifters before vowels, split two-part vowels joined). OCR readings, the word list and benchmark scoring all use the same order, so readings that look identical also vote as identical; 263 entries of the tessdata word list itself were in legacy order (for example ស្រ្ត for ស្ត្រ). Remove isolated symbol/number tokens with three or more noise symbols of at least two different kinds (for example, `#10#$`). Preserve ordinary punctuation, prices, references, formulas, repeated separators, and tokens containing letters or combining marks. Keep the original OCR text on changed pages so it can be restored. This is a conservative heuristic, not recognition of the missing source text.
9. Keep pages separate for review and editing; join the edited text for export. Corrections run once when OCR finishes, so they do not alter subsequent edits.

Accurate mode explicitly detects ordinary WebAssembly SIMD support and selects the compatible SIMD or portable core. This avoids [Tesseract 7's relaxed-SIMD float-model crash](https://github.com/naptha/tesseract.js/issues/1080). Fast integer models can use the runtime's automatic core selection.

This bypasses bad PDF text mappings, but it cannot fix a page whose visible glyphs are already wrong. Image OCR also introduces recognition errors of its own. Tesseract confidence is a review signal, not a measured probability that the Khmer is correct.

## Safeguards added November 16, 2026

- **Word list ships with every build.** `assets/khm-words.txt.gz` is tracked; `npm run assets` (also `postinstall`) unpacks it and fails if it looks incomplete. Before this, fresh installs and deployments silently voted without it.
- **Boxes follow the reading they came from.** The vote reports which reading supplied the line structure, and that reading's own crop scale maps its boxes back to the page. Previously boxes from the enlarged or reduced variants were mapped with the standard scale, so heading and word rechecks could crop the wrong pixels.
- **No lost lines.** Each row region is checked against the page reading (`coverPageLines`). An empty row is retried once with the other segmentation mode, then filled from the page reading's lines there; a row that kept under half the letters of a confident page line uses the page line; confident page lines outside every row region are inserted in reading order. The row pass is then accepted only if every region with text evidence has a reading (previously 85% of rows was enough).
- **Voting stops early only when it is settled**: once three readings are identical the remaining two cannot outvote them. Stopping after two agreeing models was measured and rejected: they share mistakes such as a stray space before a final consonant.
- **Disagreements are shown.** Spans where no option had a majority, or the word list overrode the vote, are added to the page's "check possible misread words" notice, even when the engine was confident. A voted line's confidence is capped by the readings' agreement, and the page confidence is the letter-weighted line confidence. Word boxes keep their text only when the voted words line up one-to-one, so word rechecks never act on text that is no longer in the line.
- **Benchmark measures shipped output.** `npm run benchmark:files` now runs the same final step as the browser (`src/lib/ocr-finalize.ts`: heading rechecks, word review, formatting) and reports, per page and per split, character errors without whitespace, character errors with spaces kept, reference lines missing or more than 30% wrong, lines out of order, missing numbers, review words and time. Reference samples carry `split` (`tuning` or `heldout`) and `verified`; all four current pages are `tuning` and unverified, and the report says so.

On the four benchmark pages these changes left character errors at 1.59% (63 to 62 errors), with spacing errors 2.38% to 2.35% and about 6% less time. Sauvola and adaptive Otsu thresholding as extra line readings (`OCR_LINE_VARIANTS=sauvola,adaptive`) were measured at 1.64%–1.77% and are off by default.

## Headings and the word list, November 16, 2026 (second pass)

Reported on `testkhmer2.pdf` page 2: the chapter and lesson headings came out as `ដីពួក១ ទពផែនដី`, joined to the next line, and `ខ្ល៖` was not corrected to `ខ្លះ`.

- **Rows are split at wide gaps** (`splitWideGaps`). A row such as `ជំពូក១ … ភពផែនដី` holds two headings; read as one line, the language model filled the gap with Latin (`fifa`, `Han`) and the readings no longer lined up for the vote. Each piece wider apart than 2.5 times the ink height is now read and voted on by itself, then put back on one line, and that line is always its own paragraph. Isolated specks (lower than 30% of the line, or under 10% ink) more than a word space from the text are left out; they were being read as `”`, `.` and `'`.
- **The word list counts pieces, not only unknown letters.** The tessdata list contains fragments such as `ខ្ល`, `កី` and `សំណរ`, so nearly any misreading is "all known words". What separates right from wrong is that correct text splits into fewer, longer entries. After the vote, each letter may be replaced by a letter one reading saw, or by a look-alike no reading saw (`៖/ះ`, `ី/ឺ/៏/៍`, `ិ/ឹ/ឺ`, `ុ/ូ/ួ`, `ដ/ជ/គ`, `ព/ភ`, `ទ/ម`), when that gives fewer pieces without more unknown letters. A look-alike no reading saw must be the only one that helps. Letters are never added or removed. Two neighbouring disputed letters are also tried as a pair (`គឺណែ` → `កំណែ`).
- **Measured and rejected:** letting any consonant replace any consonant, or any vowel any vowel. Applied to the four correct reference transcripts it made 15 wrong changes in 78 lines (for example `តិច` → `លិច`, `អេល្យូម` → `អេស្យូម`); the pair `ត/ល` alone made three. The short look-alike list made none.
- **A short piece standing alone is matched to the nearest single entry** (`nearestWord`): one run of 5–16 Khmer letters, optionally with a number or bullet. The heading font is misread the same way by every reading (`តពផែនដី`, `ដីពួក១`; 60 reading variants of the isolated crops never produced `ភ` or `ជំពូក`), but `ភពផែនដី` and `ជំពូក` are single entries and nothing else is as near. Cost: vowel or sign 1, look-alike consonant 1, one other consonant 2, total at most 3; a letter some reading saw there costs nothing; a tie changes nothing. This is the one place where the output can contain a letter chosen by the word list rather than read from the pixels, so it is always listed under "check possible misread words". It can be wrong for a short unknown name that happens to sit near a dictionary entry.
- Every dictionary change is reported as a disputed span.

On the four benchmark pages: 62 → 43 character errors (1.59% → 1.10%), spacing errors 2.35% → 1.79%, missing lines 1 → 0, time 77 s → 71 s. Page 2 alone: 22 → 10. All four pages are still `tuning` pages with unverified transcripts and the rules above were chosen on them, so expect less on other documents. Still wrong on page 2: `ម៉ង់តួ` (loanword not in the list, `តូ` read as `តួ` by every reading), `អេឈ្យួម`, `អ៊ីគ្រូសែន`, `កី`, `ដចជា`. Deciding between two valid entries (`ស្នូល` or `ស្នួល`) needs word frequencies, which this list does not have.

## Next accuracy experiment

Build a small consented evaluation corpus of real Khmer PDFs, Office files, old fonts, clean print, and scans. Record corrected ground truth, then compare character error rate and page reading order across `best`, `fast`, Google Vision, and a Khmer-specific model. Test the same rendered images in every engine so rendering and recognition quality are measured separately. Use a held-out set before choosing a replacement default.

## Primary sources

- [Tesseract.js](https://github.com/naptha/tesseract.js): browser/Node WebAssembly OCR and supported API. Tesseract.js recognizes images; PDF rasterization belongs in the application.
- [Official Tesseract language data](https://tesseract-ocr.github.io/tessdoc/Data-Files): Khmer (`khm`) support; `best`/`fast` model differences and LSTM requirements.
- [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html): PDF loading and page rendering.
- [LibreOffice command-line conversion](https://help.libreoffice.org/latest/en-US/text/shared/guide/convertfilters.html): document input filters and PDF export.
- [Google Cloud Vision OCR languages](https://docs.cloud.google.com/vision/docs/languages): Khmer (`km`) is listed among supported languages.
- [Netra-OCR model card](https://huggingface.co/Darayut/khmer-text-recognition): model architecture, author-reported results, line-recognition scope, limitations, and training-data licensing notes. No Netra code or weights are included in this app.
- [An End-to-End Khmer Optical Character Recognition using Sequence-to-Sequence with Attention](https://arxiv.org/abs/2106.10875): published Khmer-specific OCR research; results refer to that paper's dataset and model.
- [VERT](https://github.com/VERT-sh/VERT): upstream UI source. Panels, uploader, navigation layout, theme styles, background vector, and typography are adapted from revision `257bcb3` under AGPL-3.0; see the project NOTICE.
